## IPC contract

- Rust is the source of truth. `tauri-specta` writes `src/ipc/bindings.ts` on every debug start and via `pnpm bindings`; CI fails if the committed file is stale.
- Wire format: camelCase fields, data enums tagged with `kind`, timestamps as `f64` unix seconds, counts and indices as `u32`.
- Every command returns `Result<T, AppError>`. The generated client returns `{ status, data | error }`; `unwrap()` turns errors into a thrown `IpcError` carrying the typed `AppError`.
- Repositories are addressed by `RepoId` from `repo_open`. The backend watches the repository and emits `repo-changed { repoId, scopes }` so queries invalidate by scope.
- Long operations (clone, fetch, pull, push, submodule update) return an `OpId` immediately and report through `op-progress` and `op-finished` events; `op_cancel` stops them.
- Every mutating command takes `dryRun`. A dry run returns `OpOutcome.preview` (ref updates, commits created or dropped, predicted conflicts) without touching disk. Confirmation dialogs, drag and drop, and AI plans all use it.
- Every applied mutation writes an oplog entry first; `undo` and `redo` restore refs, HEAD and index from it.
- Credentials: git runs with `GIT_TERMINAL_PROMPT=0` and an askpass helper that emits `credential-requested`; the UI answers with `credential_respond`.

Command groups: repo, graph, refs, worktree (staging and commit), stash, history (merge, rebase, interactive rebase, cherry-pick, revert, reset, sequencer control), conflicts, remotes, advanced (submodules, worktrees, blame, file history, reflog), oplog, ai, settings. See `src-tauri/src/commands/`.

## Agent workflow

Development is split across Claude Code subagents defined in `.claude/agents/`. Each owns disjoint paths (see `docs/PLAN.md` §3 and §6).

1. The orchestrator (the main session) changes the contract or shared config on the integration branch, then writes a dispatch: goal, owned paths, contract files, acceptance criteria, proof commands.
2. The owning agent works in its own git worktree on `feat/<area>-<task>` and commits with Conventional Commits.
3. The checker runs the full gate on that branch. It fixes small integration issues and returns larger ones to the owner with a failure report.
4. On PASS the branch is rebased onto the integration branch and fast-forward merged. At each milestone the integration branch goes to `main` through a pull request.
